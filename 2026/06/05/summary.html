Anthropic이 Claude Web, Claude Code, Cowork 3개 제품 각각에 맞춘 에이전트 봉쇄(containment) 아키텍처 구축 경험을 공개했다. 위험을 '실패 가능성 × 피해 규모' 2개 요소로 정량화하는 프레임워크를 제시한다.

에이전트 능력과 접근 권한이 커질수록 피해 반경도 비례해 확대된다는 원칙 아래, 안전 장치와 모델 학습이 '실패 가능성(P_failure)'을 낮추는 역할을 담당한다. 3개 제품에서 각기 다른 봉쇄 수준을 결정한 실제 사례는 AI 에이전트 설계 벤치마크로 기능한다.

  • 위험 = 실패 가능성(P_failure) × 피해 규모(C_harm) 공식
  • 안전 장치 + 모델 학습 → P_failure 감소
  • 3개 제품별 봉쇄 아키텍처 비교: Claude Web / Claude Code / Cowork
  • 에이전트 접근 권한 확대 시 피해 반경 비례 증가 원칙
  • 프로덕션 배포 경험 기반 실전 설계 인사이트

배경 AI 에이전트가 웹 브라우징, 코드 실행, 파일 접근 등 실제 시스템 권한을 갖게 되면서 안전 설계가 핵심 과제가 됐다. Anthropic은 자체 제품군에서 이 문제를 직접 해결해야 했으며, 그 경험을 공개 공유하는 것은 업계 표준 형성에 기여한다.

토론 GeekNews(xguru)에서 소개됐으며, AI 에이전트 설계 실무자들이 즉시 참조할 수 있는 구체적 아키텍처 사례로 주목받았다.

결제 캡처·주문 처리 등 exactly-once 실행이 필요한 멀티스텝 워크플로우를 별도 Temporal 서비스 없이 기존 Postgres만으로 구현 가능하다는 주장의 실제 트레이드오프를 명확히 한다. 단, 앱 DB에 오케스트레이션 부하를 추가하는 위험을 함께 경고한다.

  • Temporal 방식: 별도 중앙 오케스트레이터 서비스 + 워커 분리
  • DBOS 방식: 워커가 DB에 직접 체크포인팅 → 크래시 후 마지막 완료 스텝부터 재개
  • 핵심 보장: Exactly-once 실행 (중간 크래시 시 완료된 스텝 재실행 방지)
  • 적용 사례: 결제 캡처, 주문 이행 등 이중 실행 비용이 발생하는 작업
  • 위험: 앱 DB와 동일 Postgres에 오케스트레이션 부하 추가
  • HN 306점·132댓글로 커뮤니티 검증

배경 Temporal은 강력하지만 별도 클러스터 운영 비용이 크다. DBOS는 이미 Postgres를 사용하는 팀이 추가 인프라 없이 durable execution을 달성할 수 있다고 주장한다. HN 스레드는 '안도감(서비스 하나 줄이기)'과 '경고(DB 부하 증가)' 두 반응으로 갈렸다.
